# Spaces Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add admin-controlled groups of devices ("spaces") whose members can all send to each other. Private pairings stay private.

**Architecture:**
- **Relay:** spaces become their own records (`spaces`, `space_members`). Pairing codes gain a kind, so that invites reuse the claim/accept/reject machinery. `/v1/peers` returns paired devices plus one entry per (space, fellow member). `/v1/send` allows "paired, or sharing the given space".
- **Clients:** `groupDestinations` (from the main-window plan) gains space groups, and each send carries the `spaceId` of the card it was sent from.
- **Runs after:** `2026-11-20-pc-main-window.md` (needs `Nicknames`, `groupDestinations`, `MainWindow`, `DevicesTab`).

**Tech Stack:** Ktor 3.3 server + SQLite (`Store.kt`), kotlinx.serialization protocol, Ktor client, Compose Desktop, Jetpack Compose.

**Spec:** `docs/superpowers/specs/2026-11-20-spaces-design.md` (read it with this plan, including its "Decisions settled" section).

## Global Constraints
- Admin-only: invite, accept/reject a join, remove a member, rename, delete, transfer admin. Every one is checked on the server.
- Limits: 50 spaces per device and 50 members per space, set by env `MJOLNIR_MAX_SPACES` / `MJOLNIR_MAX_MEMBERS`. Space names are at most 40 characters.
- Invite codes use the pairing code format and lifetime (`Limits.PAIRING_TTL_MS`). Each device has one active pairing code plus one active invite per space it administers. Codes share the claim rate-limit counter.
- *Take over as admin* is allowed only when the admin's `last_seen` is more than 30 days old. `last_seen` is written at most once a minute per device.
- A device that is both paired with you and in a shared space appears only under *My devices*. A device in two of your spaces appears under both.
- A delivery carries `space: SpaceRef?`, set from the send's `spaceId`. Labels read `From {name} · {space}`.
- Exact new copy:
  - `That's a space invite. Use Join a space.`
  - `That's a pairing code. Use Pair a device.`
  - `This device is already in {space}.`
  - `{device} wants to join {space}`
  - `Joined {space}`
  - `{space} was deleted.`
  - Buttons and headings: `New space…`, `Join a space`, `Invite…`, `Remove`, `Rename space`, `Delete space`, `Make admin`, `Take over as admin`, `Leave space`, `· admin`, `Spaces`
- Older apps keep working: `Peer.space` and `Delivery.space` are optional fields. `DELETE /v1/peers/{id}` on a peer you only share a space with returns 404 and changes nothing.
- Guest devices (`DeviceKind.GUEST`, added later) can never join a space. Leave a `// guest check added by guest-room plan` hook in `joinSpace` only if the kind doesn't exist yet.

## Review Focus
1. **A member removed mid-send:** an upload in progress when the sender is removed from the space ends with a NOT_PAIRED failure in the outbox and the existing "not paired" message. It must not retry forever. Tested in S2 (`sendAfterRemovalIs403`) and S3 (`outboxStopsOnNotPairedForSpace`).
2. **Space deleted while its invite code is showing:** claiming that code gives the generic code-not-found message, and the admin's invite view returns to the space list. Tested in S2 (`inviteForDeletedSpaceIsNotFound`).
3. **The same device reached through two spaces:** selecting it highlights both cards, and the send uses the clicked card's space. Tested in S3 (`selectingHighlightsAllCardsOfDevice`, `sendCarriesClickedSpace`).
4. **Two admins acting at once** (transfer admin while the old admin removes a member): no lost admin and no orphaned space. Exactly one admin exists afterwards. Tested in S1 (`transferIsAtomic`).
5. **Fifty-first member or space:** refused with a clear message rather than a 500. Tested in S2 (`memberLimit`, `spaceLimit`), with client copy `This space is full (50 devices).` / `You're in the most spaces allowed (50).`

### Task S2: Relay routes and rules

**Files:**
- Create: `server/src/main/kotlin/app/mjolnir/server/SpaceRoutes.kt`
- Modify:
  - `PairingRoutes.kt`: claim honours `expect` and `kind`; accept on `SPACE_INVITE` does `addMember` and emits `SpaceChanged` to all members.
  - `SendRoutes.kt`: authorises "linked, or `spaceId` given and `shareSpace`"; stores `space_id` / `space_name` on the delivery.
  - The `/v1/peers` handler adds space entries.
  - `RelayModule.kt`: registers the routes, calls `touchLastSeen` in the auth `validate`, and reads the limit env vars.
- Test: `server/src/test/kotlin/app/mjolnir/server/SpaceRoutesTest.kt` (new), plus extensions to `PairingRoutesTest.kt` and `SendRoutesTest.kt`

**Interfaces:**
- Consumes: the S1 store and models.
- Produces (endpoints; all authenticated; errors as `ErrorResponse(error)`):
  - `POST /v1/spaces` with `CreateSpaceRequest` → 201 `Space`. Errors: 400 `invalid_name`, 409 `space_limit`.
  - `GET /v1/spaces` → `List<Space>` (the caller's spaces)
  - `PATCH /v1/spaces/{id}` with `RenameSpaceRequest` → `Space` (admin)
  - `DELETE /v1/spaces/{id}` → 204 (admin). Emits `SpaceDeleted` to the other members.
  - `POST /v1/spaces/{id}/invites` → 201 `PairingCodeResponse` (admin)
  - `DELETE /v1/spaces/{id}/members/{deviceId}` → 204. The admin may remove others. Any member may remove itself (leave), except the admin, who gets 409 `admin_must_transfer`.
  - `POST /v1/spaces/{id}/admin` with `TransferAdminRequest` → `Space` (admin; the target must be a member)
  - `POST /v1/spaces/{id}/takeover` → `Space` (member; 409 `admin_active` unless the admin was last seen more than 30 days ago)
  - Non-admin calls to admin routes → 403 `not_admin`. A non-member → 404.
  - Claim errors:
    - wrong kind → 400 `wrong_kind_space` / `wrong_kind_pairing`
    - already a member → 409 `already_member`
    - the space is full → 409 `member_limit`
    - an invite whose space is gone → 404
